# omniwrap-sdk

Executable SDK generated by OmniWrap from the semantic API contract `OmniWrap`.

```javascript
const { Client } = require('omniwrap-sdk');
const client = new Client({ baseURL: 'https://omniwrap.net' });
```
Every flat operation method keeps its exact `operationId` name.


Operations are grouped into resource accessors derived from the contract's
tags or path segments, so calls read as `client.<resource>.<method>()`:

<!-- omniwrap-resource-example:javascript -->
```javascript
async function runResourceExample(client) {
  return await client.context.getUser();
}
```


The client preserves OpenAPI parameter serialization, every request media type and
successful response descriptor, injected Fetch transports, authentication, timeouts,
idempotent retries, raw responses, typed errors, and streaming.


## Error taxonomy

Every error this SDK raises extends `OmniWrapError`, so one `catch` can cover
the whole surface. Below it, `APIError` carries `status`, `headers`, `body`,
`code`, `operation`, `requestId`, `attempts` and `retryable`.
A recognized `error.code` selects the more precise class before the HTTP status fallback:

| `error.code` | class |
| --- | --- |
| `authority_unavailable` | `AuthorityUnavailableError` |
| `binding_conflict` | `BindingConflictError` |
| `configuration_required` | `ConfigurationRequiredError` |
| `cursor_expired` | `CursorExpiredError` |
| `cursor_invalid` | `CursorInvalidError` |
| `forbidden` | `ForbiddenError` |
| `idempotency_conflict` | `IdempotencyConflictError` |
| `internal_error` | `InternalError` |
| `invalid_request` | `InvalidRequestError` |
| `not_acceptable` | `NotAcceptableError` |
| `not_found` | `NotFoundError` |
| `precondition_failed` | `PreconditionFailedError` |
| `precondition_required` | `PreconditionRequiredError` |
| `rate_limited` | `RateLimitedError` |
| `request_too_large` | `RequestTooLargeError` |
| `retry_requires_reconciliation` | `RetryRequiresReconciliationError` |
| `source_not_valid` | `SourceNotValidError` |
| `unauthenticated` | `UnauthenticatedError` |
| `unsupported_media_type` | `UnsupportedMediaTypeError` |

Unknown codes continue through the status table, and an unknown code/status
combination remains `APIError`:

| status | class |
| --- | --- |
| 400 | `BadRequestError` |
| 401 | `AuthenticationError` |
| 403 | `PermissionDeniedError` |
| 404 | `NotFoundError` |
| 409 | `ConflictError` |
| 422 | `UnprocessableEntityError` |
| 429 | `RateLimitError` |
| >= 500 | `InternalServerError` |
| anything else | `APIError` |

```javascript
try {
  await client.getUserContext();
} catch (error) {
  if (error instanceof NotFoundError) return null;
  if (error instanceof RateLimitError) return retryLater(error.headers["retry-after"]);
  throw error;
}
```

The message is the peer's own words when the body carries them -- `error.message`
inside an `{"error": {...}}` envelope, else a flat `message`, `detail` or
`title` -- prefixed by the status, and `{status} status code (no body)` when the
body says nothing. It is bounded at 4096 characters; `error.body` keeps the
whole payload either way.

A caller-supplied `AbortSignal` raises `APIUserAbortError` (fixed message
`Request was aborted.`); a signal that is already aborted rejects before any
fetch dispatch. A transport failure raises `APIConnectionError` (message
`Connection error.`) and an expired client timeout raises `APITimeoutError`
(message `Request timed out.`, with the configured `timeout`). A malformed JSON
body on a success status lets the decode `SyntaxError` escape untouched and is
never retried. The retryable statuses are 408, 409, 429 and every 5xx when no
`x-should-retry` header is present, and a retry only happens for idempotent operations or requests carrying an
idempotency key. `ClientOptions.apiKey` feeds the contract's security scheme
whatever its type when exactly one scheme is declared. When every operation
requires authentication, constructing a client without `apiKey`, `accessToken`,
`auth`, or a `hooks.beforeRequest` credential injector throws
`MissingCredentialsError` -- an `AuthenticationError` with no `status`, because
no request was ever sent.

SDK transport, HTTP, argument and credential errors carry `error.remediation`, a JSON object an
agent or a log pipeline can act on: a stable `code` (`authentication_failed`,
`not_found`, `rate_limited`, `validation_failed`, `missing_argument`,
`timeout`, ...), the `cause` (the server's RFC 9457 `detail` when it sends
one), a suggested `action`, `retryable` and `docs`. Where they apply it names
the SDK `parameter` and JSON `pointer` at fault, the security `schemes` and
`credentialOptions` of a refused credential, the server-directed `retryAfter`
in seconds and per-field `fields` errors. Configured credential values are
redacted from it.

```javascript
catch (error) {
  const recovery = error.remediation?.recovery;
  if (recovery?.outcome === "in_doubt" && !recovery.retry_safe) {
    // Reconcile with the server before considering another mutation.
    console.log(recovery);
  }
}
```

`error.remediation.recovery` is a versioned `omniwrap.sdk-recovery/v1`
observation: `before_effects` for local validation/authentication refusal,
`acknowledged` for successful HTTP response decoding failures, and `in_doubt`
for possible mutations. Only read-only operations can set `retry_safe: true`;
apply bounded retries and server wait guidance. An HTTP error status, inferred
idempotence or model suggestion never authorizes replay of an uncertain mutation.
Successful JSON parse errors retain their original `SyntaxError` identity.
The binding names the operation, contract fingerprint, source/package versions
and deterministic projection digest, not an archive hash or signature. Export
only the recovery object to Studio's local SDK delivery inspector. User hook or
native argument-binding errors may lack this record. Existing automatic
transport retry and authentication options retain their behavior.

A cookie security scheme has a second, browser-owned path. Pass a fetch
`credentials` mode (`same-origin` or `include`) and the client forwards it to
every request while leaving the cookie to the user agent: an `HttpOnly` session
cookie is attached by the browser, is never readable from script, and this
client neither asks for it nor writes a `Cookie` header. Such a client can be
constructed without a credential. Passing the cookie's value explicitly through
`auth` keeps the server-side behaviour and writes the `Cookie` header itself.

## Idempotency keys

A POST is retried only under an `Idempotency-Key`. Pass one per call as
`idempotencyKey`, or let the client mint a UUID: a POST the contract marks
idempotent always receives one, and `new Client({ autoIdempotencyKey: true })`
extends that to every POST. A retried attempt replays the key the first attempt
sent, so the peer can deduplicate it.

## Retries

`maxRetries` (default 2) bounds the attempts. The server's own verdict wins:
`x-should-retry: true` or `false` overrides the status policy, and its wait is
honoured from `retry-after-ms`, then `Retry-After` (seconds or an HTTP-date),
then an IETF `RateLimit` reset (`t=` or `RateLimit-Reset`). Without one, waits
back off exponentially with jitter. A server asking for longer than
`maxRetryDelay` (default 60000 ms) gets its error surfaced at once, since a
retry it said would fail only adds load; `retryBudget` caps a whole call,
waits included.

`fallbackBaseURLs` lists ordered alternates to the base URL. Only idempotent
operations use them, and only after a connection failure or a 5xx; each
hook context carries the `baseURL` its attempt targeted, so `onRetry` and
`afterResponse` record which endpoint answered.

```javascript
const client = new Client({
  maxRetries: 3,
  retryBudget: 20000,
  fallbackBaseURLs: ["https://eu.example.com"],
  hooks: { afterResponse: ({ baseURL, status }) => console.log(baseURL, status) },
});
```

## Request identity

Every parsed JSON object names the request that produced it and reaches the
response it arrived on, with no `rawResponse: true` needed:

```javascript
const value = await client.getUserContext();
console.log(value._request_id, value._response.status);
```

Both properties are non-enumerable, so spreads, `Object.keys` and
`JSON.stringify` still see exactly the payload the peer sent. `_request_id` is
the `x-request-id` header (or `request-id`), or `null` when the peer sent
neither. Convention-based pages leave them on `page.body`. An explicitly
selected response-envelope page keeps `page.body` untouched and exposes the
response itself as `page.response`.

## Named optional arguments

A few operations take their optional arguments as one named object rather than
positionally:

```javascript
await client.createReport({ body: { title: "q3" }, filter: { status: "open" } });
```

Three cases get this treatment. First, two optional slots that both accept a
plain object -- an optional JSON body beside an exploded `deepObject` query
parameter, say. Second, an operation with an optional body where some two
optional slots accept a common type: the body and a parameter, or two
parameters with the body merely sitting beside them. Third, two optional slots
that accept a common type and send it to different parts of the request -- an
`include` query parameter beside an `openai-beta` header, say.

In all three, a lone positional argument could have been meant as either slot,
and passing it positionally could not say which. What makes that harmful is
where the unplaceable argument lands: it stays in the first optional position,
which is the request body when the operation has one, and otherwise the first
optional parameter -- so it is sent as the wrong part of the request entirely.
Naming the slot says which was meant, and an unrecognized key is
refused by name instead of being routed somewhere.

Two optional parameters that accept a common type and bind to the SAME part of
the request keep the positional shape: the fallback leaves such an argument in
the first of them, which is where reading the signature left to right says it
goes.

When a success response offers both a buffered representation and a stream, the method defaults to the buffered response. Pass `{ streamResponse: true }` as request options to receive the stream.


SSE operations yield `SSEEvent<T>` values: the decoded payload is `event.data`,
beside the frame's own `id`, `event` and `retry` metadata, so a payload key is
never shadowed. Set `sse.lastEventId` for manual resumption or a bounded
`sse.maxReconnects` for automatic Last-Event-ID reconnects.

## Hooks and tracing

`hooks` observes every call. Each attempt starts with `beforeRequest` and ends
with exactly one of `onRetry` (another attempt follows), `afterResponse` (the
success the call returns) or `onError` (the failure it throws): a call that
succeeds after one retried 503 reports `beforeRequest`, `onRetry`,
`beforeRequest`, `afterResponse`, and a connection failure that is not retried
reports `beforeRequest`, `onError`. Every context carries `operationId`,
`method`, `url`, `headers`, `attempt` (from 1) and `elapsedMs` since the call
started; `status` is set once the server answered, `error` when the attempt
failed, and `wait` (milliseconds) on `onRetry`.

No context carries a credential. `Authorization`, `Proxy-Authorization`,
`Cookie`, every API-key header and every API-key query parameter read
`[redacted]`, in `headers` and in `url`, and so does a configured credential
value found anywhere else. `afterResponse`, `onRetry` and `onError` receive
frozen copies (`HookContext`): they are read-only and changing them changes
nothing on the wire. `beforeRequest` is the one hook that may change the
request, as documented under Per-request credentials. A hook may be async; its
own failure reaches the caller and is never retried.

`tracer` opens one span per call without any tracing dependency. The client
calls `tracer.startSpan(operationId, { "http.request.method": method })`
before the first attempt and `span.end(attributes)` when the call settles, with
`http.request.resend_count` (the retries) and, when the server answered,
`http.response.status_code`. With `@opentelemetry/api` installed, this adapter
maps it onto OpenTelemetry:

```javascript
const { trace } = require("@opentelemetry/api");

const otel = trace.getTracer("my-service");
const tracer = {
  startSpan(name, attributes) {
    const span = otel.startSpan(name, { attributes });
    return {
      end(attributes) {
        span.setAttributes(attributes);
        span.end();
      },
    };
  },
};
const client = new Client({
  tracer,
  hooks: {
    onRetry: ({ operationId, attempt, status, wait }) => console.log(operationId, attempt, status, wait),
    onError: ({ operationId, url, status, error }) => console.error(operationId, url, status, error),
  },
});
```

## Per-request credentials

`hooks.beforeRequest` runs immediately before every attempt and receives a
mutable `RequestContext`:

| field | meaning |
| --- | --- |
| `operation`, `operationId` | `operationId` of the call in flight |
| `method` | uppercase HTTP method |
| `path` | request path, path parameters already substituted, no query |
| `url` | fully rendered URL, query included as it stands when the hook runs |
| `headers` | outgoing headers; assign a key to add or replace it |
| `query` | outgoing query parameters; assign a key to add or replace it |
| `body` | the encoded body handed to `fetch`, exposed for signing |
| `attempt` | 1-based attempt counter |
| `baseURL` | the base URL this attempt targets |
| `elapsedMs` | milliseconds since the call started |

Credentials are masked here too: a credential header or query parameter reads
`[redacted]`. Leave it as it is and the real value is sent; assign it to
replace the credential, or delete it to drop it. A signature that must cover a
credential reads that credential from your own configuration.

Writes to `headers` and `query` are honored: the request is sent with the
headers the hook leaves behind, and the URL is re-rendered from `query` after
the hook returns. This is what makes a credential bound to the request itself
expressible, such as an intent-bound action token, AWS SigV4, an HTTP
Signature, DPoP, or Hawk:

```javascript
const client = new Client({
  hooks: {
    beforeRequest: async (context) => {
      context.headers.authorization = await sign(context.method, context.path);
    },
  },
});
```

Each attempt gets its own copies, so a retry is presented with unsigned headers
and is signed again rather than carrying a stale signature. Replacing
`context.body` does not change what is sent, and `query` writes are ignored on
requests that target a URL the peer supplied (Link pagination, SSE reconnect).
A hook that reads only the previously available fields keeps working unchanged.
